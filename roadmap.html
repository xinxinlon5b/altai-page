① 灰度上线：从「自测通过」到「真实放量」

P0 · 最优先
现状缺口：只发给自己测试过，没在真实客户账号上跑过。这是 87 分最大的水分——系统「能跑」和「敢真发」是两回事。

→

→

1

注册测试小号（账号要求）

  • 账号来源：客户本人或员工手机号注册，绝不用买来的号（风控高、易封）
  • 手机号：一个平台一个号，实名绑定，能收验证码
  • 注册地点/网络：用目标国网络（俄区）注册 VK，避免「新号 + 异国 IP」组合
  • 新号冷静期：注册后先养 2-3 天（浏览、加 3-5 个好友、发 1-2 条动态），不要当天就发私信
2

小号名字 / 头像 / 资料倾向（方便客户有好感）

  • 名字：像真人，用常见俄语名 + 行业词（如 Алексей Логистика），不要「物流公司」「货运代理」这种广告味名字
  • 头像：真人感照片（可授权使用的图），不要 logo、不要风景图
  • 简介：一句话业务向，像个人在做（「помогаю с доставкой из Китая» 帮中国发货），不像公司客服
  • 性别/年龄：与业务匹配，30-45 岁商务感最佳
3

配置灰度参数（staged_go_live.py 执行器）

  • 白名单：3-5 个测试小号（可以是你自己的小号，也可以客户提供的）
  • 日上限：20 条 / 天（首日可再降到 10 条）
  • 频率：5 条 / 小时（均匀分布，不要一口气发完）
  • 时段：目标时区 10:00-19:00（客户在线时）
  • 熔断：遇到平台风控响应码（429/403/验证码）→ 立即全停，人工看原因再恢复
4

执行灰度（48 小时）

  • D3-D4：只发白名单小号，目标 20-40 条/号，观察送达率、回复率、风控触发
  • D5-D6：逐步放开到真实线索（先从评分 high 的 450 条里选 50 条），日上限提到 50 条
  • 全程：发送闸门（send_guard）保持 authorize 才发，绝不裸发
5

出试运行报告（D7）

  • 指标：送达率 ≥ 90%？回复率 ≥ 3%？风控 0 次？
  • 记录：发了多少、回复多少、哪些话术效果好、哪些平台有问题
  • 决策：达标 → 正式放量；不达标 → 定位问题（话术？时段？账号？）再调

90%

≥3%

🚦 熔断规则（出问题立即全停）
  • 429（限流）→ 停 2 小时
  • 403（风控）→ 停 24 小时 + 人工检查
  • 验证码弹窗 → 立即全停 + 人工处理
  • 连续 3 条失败 → 熔断自动触发
  • 恢复前必须人工确认原因
⏱ 灰度节奏表
  • D1-2：注册小号 + 养号 + 配置参数
  • D3-4：白名单 3-5 号，日 20 条
  • D5-6：放开真实线索，日 50 条
  • D7：试运行报告 + 放量决策
  • 全程 send_guard 守护，绝不裸发
小白解读：就像新店开业先请亲戚朋友来试吃（白名单小号），好吃再对外开放（真实放量）。前 7 天是「试营业」，随时可以关门调整，不会砸招牌。

  • 优先级 2：钉钉群/企业微信——团队级

只有 修不了 / 需要客户操作（如重新扫码登录） 的事才告警到客户。

小白解读：就像给系统装了个「健康手环」，每 30 分钟测一次体温（进程）、血压（数据库）、血糖（磁盘）。小毛病手环自己调理（自动重启），大毛病才打电话给你（告警）。客户全程不用管。

  • 25-35 分钟：功能演示——线索采集 → AI 评分 → 画像 → 话术生成
  • 35-45 分钟：容错演示——故意 kill 进程看自愈、断网看熔断

⑤ 解绑 Hermes：Docker 容器化（你最关心的问题）

P2 · 加分
现状缺口：技能/插件/调度绑在 Hermes 上，客户 IT 要求 Docker 或自托管时无法交付。
❓ 你说的「依赖审计 + 纯 Python 调度器 + Docker 镜像」是什么意思？

打个比方：现在你的系统像一台「一体机」——屏幕、主机、键盘焊死在一起（都绑在 Hermes 里）。Docker 化 = 把「主机」（核心获客逻辑）单独拆出来，装进一个标准集装箱（Docker 镜像），这个集装箱放在任何电脑上都能跑，不需要装 Hermes。

  • 依赖审计：盘清楚核心获客逻辑到底用了哪些库（不依赖 Hermes 的那些），列出清单
  • 纯 Python 调度器：把「定时采集/发送/报告」从 Hermes 的 cron 换成独立 Python 调度（APScheduler 之类），不依赖 Hermes 进程
  • Docker 镜像：把核心逻辑 + 依赖 + 调度器打包成一个镜像，`docker run` 就能启动，43 项验收在容器内复验
🟦 模式 A：Hermes 版（当前）
  • AI 对话 + 获客 + 看板全家桶
  • 适合你现在的交付（客户不懂技术）
  • 开箱即用，人机交互体验好
  • 缺点：客户 IT 要求 Docker 时交付不了
🟩 模式 B：Docker 版（新增）
  • 核心获客逻辑独立跑（采集/评分/话术/发送/报告）
  • 适合客户有 IT 团队、要求自托管的场景
  • 更稳定（不依赖桌面应用，7×24 跑）
  • 缺点：没有 AI 聊天界面，运维门槛高一点
🤔 那为什么还要用 Hermes？

因为 Hermes 是「驾驶舱」，Docker 是「发动机」，两者不是替代关系：

  • Hermes 的价值：AI 对话、智能决策、人机协作、快速迭代——这是你的核心优势
  • Docker 的价值：稳定执行、客户 IT 认可、可规模化部署
  • 最佳实践：同一套核心逻辑，两种包装。客户要简单 → 给 Hermes 版；客户要 Docker → 给容器版。报价还能加码
📈 Docker 版会更稳定吗？
  • 更稳定：不依赖图形界面/桌面应用，纯服务 7×24 跑
  • 更标准：客户 IT 团队熟悉 Docker，运维交接更容易
  • 但不是「更高级」：损失了 AI 对话能力，纯执行流水线
  • 结论：Docker 是「交付选项」不是「升级」，按客户需求二选一或都要
1

依赖审计（半天）

  • 列出获客核心模块的 Python 依赖（requests/apscheduler/pandas 等）
  • 区分：哪些依赖 Hermes（AI 对话） vs 哪些独立（采集/发送）
  • 产出：依赖清单 + 独立可运行性评估
2

纯 Python 调度器（1-2 天）

  • 用 APScheduler 重写定时任务（采集/评分/发送/报告）
  • 发送闸门（send_guard）逻辑原样保留——安全红线不因换壳妥协
  • 产出：独立可跑的调度服务
3

Docker 镜像（1 天）

  • 写 Dockerfile：Python 3.11 + 依赖 + 调度器 + 配置文件
  • 数据卷挂载：客户数据在宿主机（可备份、可迁移）
  • 产出：可 `docker compose up` 一键启动
4

容器内复验 43 项（1 天）

  • 在容器内重跑验收（安全红线优先）
  • 双运行模式文档化：Hermes 版 / Docker 版各一份部署手册
  • 产出：交付选项 +1，报价加码
小白解读：现在系统像「苹果一体机」——好用但客户想拆开换零件（自托管）不行。Docker 化 = 做出一个「标准主机箱」，任何懂电脑的人都能自己装。但一体机还是卖给普通客户，主机箱卖给有 IT 的客户——两种都卖，生意更大。

⑥ 多租户舰队：1 台电脑管 N 个客户

P3 · 远期
现状缺口：目前一台电脑服务一个客户，客户多了电脑也多——人力成本线性增长，生意做不大。
中央控制台（你的电脑）
⇄
客户 A 隔离区
客户 B 隔离区
客户 C 隔离区
1

数据隔离（第一原则）

  • 每个客户一个独立数据目录：~/.hermes/data/clients/<客户A>/
  • 独立登录态（cookie 互不干扰）、独立话术引擎、独立看板端口
  • 客户 A 的 AI 永远看不到客户 B 的数据（目录隔离 + 权限隔离）
2

中央控制台（你的操作台）

  • 一个网页/面板：看到所有客户的状态（绿/黄/红）
  • 批量操作：统一发更新、统一升级话术引擎
  • 告警汇聚：所有客户的问题集中到你的微信
3

复用已有基础

  • Tailscale 1 对 N 组网已经就绪（lon5blon5b@）
  • 安装器 + 验收体系可以模板化（边际成本递减）
  • 先跑 2-3 个客户验证单客户模式，再横向扩展
💰 为什么是关键一步
  • 交付生意（一单一做）→ 订阅生意（持续收费）
  • 1 台电脑管 N 客户 = 人力成本不涨，收入涨
  • 模板化交付：下一个客户 3 天装完，不是 7 天
🗺 落地路径
  • 现在：把当前交付流程固化成「安装器 + 验收 + 文档」模板
  • 短期：第 2、3 个客户按模板交付，验证可复用
  • 中期：做中央控制台 + 多客户隔离
  • 远期：订阅制（年费 1.5-3 万 / 客户）
小白解读：现在一个客户一台电脑 = 开一家店雇一个店长。多租户 = 一个中央仓库 + 每个客户一个「独立货架」（隔离区），一个仓管（你）管所有货架。客户多了不用雇更多店长。

⑦ 员工协作：让 10+ 员工一起用，但带不走数据

P3 · 你要的新方案
你的需求：未来 10 多个员工都能用这个项目干活，但他们只是「使用 + 转人工」，员工流失后带不走任何数据，同时降本增效。
🎯 核心思路：数据不落地，员工只碰「操作界面」

员工的电脑上不存任何客户数据——所有数据都在你的服务器/控制台。
员工通过网页工作台操作：看线索、选话术、点发送、转人工。
就像银行柜员——柜员能操作你的账户，但钱不放在柜员口袋里。

员工工作台（网页）
→
中央服务器（数据全在这）
→
平台账号（VK/WA/TG）
1

设计「员工工作台」（网页版，不装软件）

  • 员工打开网页 → 登录（账号密码 + 手机验证码）
  • 看到：待跟进线索、话术建议、一键发送、转人工按钮
  • 看不到：客户手机号明文、登录 cookie、API key、话术引擎底层

权限分层（谁能看到什么）

  • 员工（普通）：只能看分配给他的线索 + 操作发送/转人工
  • 组长：多看一个组的数据 + 统计报表
  • 老板（你）：全部数据 + 配置 + 导出
  • 数据导出权限 只有你有，员工永远没有
3

防带走的 5 道锁

  • 锁 1 数据不落地：员工浏览器只拿渲染后的界面，拿不到原始数据
  • 锁 2 禁止复制：客户手机号/微信号打码显示，复制即脱敏
  • 锁 3 操作留痕：每个员工的操作都有日志（谁、何时、干了啥）
  • 锁 4 登录态集中：平台账号在服务器，员工手机上没有 cookie
  • 锁 5 离职即失权：账号一停，所有权限立即消失

降本增效怎么体现

  • 1 个员工能同时盯 3-5 个平台的线索（系统自动筛好）
  • AI 已写完 80% 话术，员工只做「判断 + 发送」
  • 不用雇会俄语的——AI 翻译 + 话术库
  • 员工培训从 1 个月 → 1 天（界面极简）
